exact file, function contract, constraints, and acceptance criteria. The "Output used"

post-review corrections and engineering decisions applied after inspecting the output.

## Commit 4 — `feat: BM25 index builder with joblib persistence`

**Prompt:**
> In `backend/app/search/bm25.py`, implement `BM25Index` class using `rank-bm25` (BM25Okapi). Methods: `build(docs: list[str], doc_ids: list[str]) -> None` — tokenizes on whitespace, fits BM25Okapi; `query(q: str, top_k: int) -> list[tuple[str, float]]` — returns (doc_id, score) descending; `save(path: Path) -> None` — joblib.dump to path/bm25_index.pkl; `load(path: Path) -> None` — joblib.load. Type hints required. No global mutable state. `INDEX_FILENAME = "bm25_index.pkl"` as module constant. Raise RuntimeError if query() called before build(). Raise ValueError if len(docs) != len(doc_ids).

**Output used:** BM25Index class. Reviewed for three correctness properties before adopting:

1. **Encapsulation** — BM25Okapi state lives entirely inside the class instance, not at
   module level. Satisfies the no-global-mutable-state rule; two BM25Index instances can
   coexist without interference (relevant for tests that build toy indexes alongside the
   real corpus).
2. **Error contracts** — `RuntimeError` on query-before-build gives a clear, actionable
   message to the caller. An `AttributeError` from an uninitialised `self._bm25` would
   be confusing and harder to trace. `ValueError` on length mismatch catches the most
   common integration bug — misaligned doc_ids and docs lists.
3. **Persistence design** — `joblib.dump/load` is the correct serialization choice for
   sklearn-style objects with large numpy arrays inside BM25Okapi. `pickle` would work
   but joblib handles memory-mapped arrays more efficiently. `INDEX_FILENAME` as a module
   constant ensures `save()` and `load()` always agree on the filename — no magic strings.

No structural changes required after review.

**Document section satisfied:** Section 6.2 (BM25 index, artifacts under data/index/bm25/)

## Commit 6 — `feat: vector index builder — sentence-transformers + FAISS CPU + metadata.json`

**Prompt:**

Methods: `build(docs, doc_ids)` — encodes with sentence-transformers, L2-normalize, `faiss.IndexFlatIP`; `query(q, top_k)` — encodes query, FAISS search → [(doc_id, cosine_score)]; `save(path, corpus_hash)` — faiss.write_index + doc_ids.json + metadata.json {model_name, dimension, corpus_hash, build_timestamp, num_docs}; `load(path)` — faiss.read_index + doc_ids.json; `validate_metadata(path)` — static method, reads metadata.json, raises ValueError if model_name or dimension don't match current constants (message must include "Rebuild with: python -m app.index"). **Output used:** VectorIndex class and `compute_corpus_hash()` helper. Reviewed the FAISS
index type choice: `IndexFlatIP` (inner product) combined with L2-normalized vectors
computes exact cosine similarity. Approximate indexes (HNSW, IVF) would be faster on
large corpora but introduce recall loss — on 400 docs, exact search is negligible cost
and gives reproducible results across machines.

**Edits made:**
- Set `normalize_embeddings=True` in `model.encode()` — this applies L2 normalization
  inside the batch encode loop, which is more efficient than a separate numpy
  normalization pass over the full embedding matrix after the fact.
- Added `convert_to_numpy=True` — SentenceTransformer can return a `torch.Tensor` if
  PyTorch is available. `faiss.IndexFlatIP` expects a contiguous `numpy float32` array.
  Without this flag, the type guarantee depends on the runtime environment; with it, the
  contract is explicit regardless of torch installation state.

## Commit 8 — `feat: hybrid search — min-max + z-score normalization, alpha weighting`

**Prompt:**
> In `backend/app/search/hybrid.py`, implement: (1) `minmax_normalize(scores: list[float]) -> list[float]` — scales to [0,1], guard: max==min → [0.5]*len (prevents Scenario C divide-by-zero); (2) `zscore_normalize(scores: list[float]) -> list[float]` — z-score, guard: std==0 → [0.5]*len; (3) `SearchResult` dataclass with fields: doc_id, title, snippet, bm25_score, vector_score, hybrid_score; (4) `HybridSearch` class with `search(query, top_k, alpha, filters, normalization)` — retrieves top_k*3 from each index, unions doc_ids, fills missing scores with 0.0, normalizes both score lists, computes hybrid=alpha*norm_bm25+(1-alpha)*norm_vector, post-filters on doc metadata, sorts descending, returns top_k SearchResults with highlight_snippet. Import BM25Index, VectorIndex, highlight_snippet. No global state.

**Output used:** hybrid.py with all components. Reviewed the score fusion design: retrieving
`top_k * 3` candidates from each index before unioning gives normalization a large enough
score distribution to be meaningful — normalizing a 3-element list vs. a 30-element list
produces very different relative scores.

**Edits made:**
- Changed `candidate_k = top_k * 3` to `candidate_k = max(top_k * 3, 30)` — for
  `top_k=1` requests, the original produces only 3 candidates. Normalization over 3
  elements collapses score variance; 30 is the practical minimum for minmax to spread
  meaningfully.
- Added `round(..., 6)` on all three returned scores — floating-point arithmetic without
  rounding produces values like `0.4999999999999997`, which are visually noisy in the
  dashboard score bars and in API response JSON.
- Changed `filters` default in `SearchResult` dataclass from `None` to `{}` —
  Pydantic's `SearchRequest` model defaults `filters` to `{}`. Matching defaults removes
  a `NoneType` check in the filter loop, making the iteration unconditional and cleaner.

**Document section satisfied:** Section 6.3 (hybrid scoring explicit, alpha configurable, 2 normalization strategies, score breakdown)

**Prompt:**
> In `backend/tests/test_hybrid.py`, write pytest tests for HybridSearch using a 5-doc corpus (ML, photosynthesis, quantum physics, neural networks, DNA) with category field for filter testing. Tests: (1) alpha=1.0 → hybrid_score == bm25_score; (2) alpha=0.0 → hybrid_score == vector_score; (3) alpha=0.5 → hybrid is average; (4) minmax output in [0,1], math [0.0, 0.5, 1.0] correct, NaN guard [1.0,1.0,1.0]→[0.5,0.5,0.5] (Scenario C regression), single-element; (5) zscore zero-mean, std=0 guard, sign test; (6) category filter restricts results, empty filter passes all, nonexistent filter returns []; (7) SearchResult fields present, top_k respected, scores descending.

**Output used:** test_hybrid.py. Reviewed test coverage against three correctness properties:

1. **Alpha boundary cases** — `alpha=1.0` must produce `hybrid_score == bm25_score`
   exactly, not approximately. Float equality is valid here because the formula is
   `1.0 * bm25 + 0.0 * vector = bm25` — no arithmetic error accumulates. Same reasoning
   applies to `alpha=0.0`. These two cases are the most common regression from formula
   mistakes.
2. **Normalization math verification** — `[0.0, 0.5, 1.0]` through minmax → `[0.0, 0.5, 1.0]`
   (identity when already in [0,1]). Manually verified: `min=0.0`, `max=1.0`,
   `span=1.0`, each element maps to itself. This confirms the formula is algebraically
   correct, not just that it runs without error.
3. **Regression lock for Scenario C** — `test_minmax_nan_guard` covers both
   `[1.0, 1.0, 1.0]` (all-equal nonzero) and `[0.0, 0.0, 0.0]` (all-zero, the actual
   production failure path). Both must return `[0.5, 0.5, 0.5]`. This test exists so
   a future developer cannot remove the guard and have the suite still pass.
